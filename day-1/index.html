Protocol 01

SAML 2.0 (Security Assertion Markup Language)

XML-based • Enterprise Federation
What is SAML 2.0?

An open, XML-based standard created by OASIS for exchanging authentication and authorization data across distinct security domains.

  • Federation: Linking user identities across autonomous systems without credential replication.
  • Single Sign-On (SSO): Log in once at the Identity Provider to securely access multiple independent applications.
  • User / Principal: The entity (employee/human user) attempting access.
Entities & Trust

Two primary parties form an authoritative relationship bound by public key cryptography.

  • Identity Provider (IdP): Holds user credentials, performs authentication, and issues signed assertions (e.g., Okta, Ping, Entra ID).
  • Service Provider (SP): The web application providing services (e.g., Salesforce, Workday, AWS Console).
  • Circle of Trust: Cryptographic trust established in advance via metadata exchange (X.509 certs, endpoints).
ACS & SP-Initiated SSO

How users land on the service and where assertions are consumed.

  • SP-Initiated SSO: The flow begins at the SP when an unauthenticated user visits protected resources and gets redirected to the IdP.
  • ACS (Assertion Consumer Service): The designated endpoint on the SP that receives, parses, and validates incoming SAML assertions.
  • IdP-Initiated SSO: Starts directly from the IdP portal dashboard.
Anatomy of a SAML Assertion

The XML document issued by the IdP containing verified statements regarding the user:

1. Subject
Identifies the authenticated principal via <NameID> (e.g., email or unique GUID).
2. Conditions
Validity constraints: NotBefore, NotOnOrAfter, and AudienceRestriction (SP entity ID).
3. AuthnStatement
Proof of authentication: timestamp, session index, and method/context (password, MFA).
4. AttributeStatement
User attributes shared with SP: first name, last name, department, email, security groups.
5. Digital Signature
Cryptographic XML signature verifying message integrity and authenticity via IdP certificate.
SAML 2.0 Web Browser SSO Flow (SP-Initiated via HTTP POST / Redirect) Sequence Flow
1
User → SP
User attempts to access a protected URL on the Service Provider (SP) without an active session.
2
SP → Browser
SP generates a <samlp:AuthnRequest>, base64 encodes it, and redirects browser to IdP SSO endpoint.
3
Browser → IdP
Browser follows redirect to Identity Provider (IdP); IdP challenges the user for credentials (password + MFA).
4
IdP Processing
IdP verifies credentials, generates a signed XML <samlp:Response> enclosing the SAML Assertion.
5
IdP → SP (via POST)
IdP returns an auto-submitting HTML form causing browser to HTTP POST the assertion to the SP's ACS URL.
6
SP Validation
SP validates signature via trusted IdP cert, checks conditions/timestamps, creates local session, and logs the user in.
Framework 02

OAuth 2.0 (Open Authorization Framework)

RFC 6749 • Delegated Access
What is OAuth 2.0? (AuthN vs AuthZ)

OAuth 2.0 is an authorization framework that enables third-party applications to obtain limited access to an HTTP service on behalf of a resource owner.

  • Authorization ≠ Authentication: Authentication (AuthN) answers “Who are you?” while Authorization (AuthZ) answers “What permissions do you have?”
  • Core Purpose: Eliminates the need for users to share passwords with third parties (the “valet key” pattern for APIs).
  • Delegated Access: User grants Client permission to read/write specific resources for a limited time.
The 4 OAuth 2.0 Roles

Every OAuth 2.0 interaction takes place between four clearly defined actors:

  • Resource Owner: The entity (usually the human user) capable of granting access to a protected resource.
  • Client: The application making protected resource requests on behalf of the resource owner (web app, mobile app, SPA).
  • Authorization Server: Issues access tokens after authenticating the owner and obtaining authorization consent.
  • Resource Server: The API hosting protected resources, accepting and validating access tokens.
Access Token vs Refresh Token

Credentials that represent granted authorization authority:

  • Access Token: Short-lived string/JWT used by the client to access protected APIs. Must be protected against leakage.
  • Refresh Token: Long-lived credential used exclusively with the Authorization Server to obtain a fresh access token without prompting the user.
  • Bearer Token: Possession gives access (Authorization: Bearer <token>).
Protected Resource Access

How the client communicates with the API:

  • Client includes the token in the HTTP header: Authorization: Bearer ya29.a0AfH...
  • Resource Server verifies token signature or queries the Authorization Server via Token Introspection (RFC 7662).
  • Enforces scopes: if token lacks required scope, returns HTTP 403 Forbidden.
OAuth 2.0 Authorization Code Flow (Gold Standard for Secure Apps) Sequence Flow
1
Client → Auth Server
Client redirects user to Auth Server with response_type=code, client_id, redirect_uri, and requested scope.
2
User & Auth Server
User authenticates at the Auth Server and grants consent for the requested scopes (permissions).
3
Auth Server → Client
Auth Server redirects back to Client's redirect_uri delivering a temporary, single-use Authorization Code.
4
Client → Auth Server
Back-Channel: Client exchanges the Auth Code + client_secret directly with the Auth Server token endpoint.
5
Auth Server → Client
Auth Server validates code and secret, then issues an Access Token (& optional Refresh Token).
6
Client → Resource Server
Client requests protected API using header Authorization: Bearer <access_token> to fetch data.
Identity Layer 03

OpenID Connect (OIDC)

JSON/JWT • OAuth 2.0 Extension
The Core Formula: OIDC = OAuth 2.0 + Authentication + Identity

OAuth 2.0 was explicitly designed for authorization (“can the client access my files?”), not identity. OIDC extends OAuth 2.0 by standardizing user authentication and returning an identity assertion in the form of an ID Token.

OIDC Core Terminology

Mapping OAuth roles into Identity concepts:

  • OpenID Provider (OP): The OAuth 2.0 Authorization Server capable of authenticating the End-User and issuing ID Tokens (e.g., Google, Auth0, Okta).
  • Relying Party (RP): The OAuth 2.0 Client application relying on the OP for user authentication and claims.
  • End-User: The human subject being authenticated.
  • UserInfo Endpoint: Protected OAuth 2.0 REST endpoint where the RP uses the Access Token to retrieve additional profile claims.
Access Token vs. ID Token

The critical distinction in modern IAM architectures:

  • Access Token: Intended for the Resource Server (API). Proves delegated authorization. Often opaque or JWT, but the client does NOT need to parse it.
  • ID Token: Intended for the Relying Party (Client). Proves authentication occurred and carries identity claims about the user. Always a formatted JWT.
  • Anti-Pattern: Never pass an ID Token as an API bearer authorization credential.
ID Token Structure (JWT)

Consists of three Base64URL-encoded parts separated by periods (header.payload.signature):

  • Header: Token type (JWT), signing algorithm (RS256), and key ID (kid).
  • Payload: Set of verifiable claims about the user and authentication event.
  • Signature: Cryptographic signature generated by the OP private key; verified by RP using the OP's public keys (from jwks_uri).
Key Claims & Scopes

Standard assertions conveyed inside the ID token:

  • iss (Issuer): URL of the OP that issued the token.
  • sub (Subject): Unique, persistent identifier for the user.
  • aud (Audience): Must match the Client's client_id.
  • exp / iat: Expiration timestamp & Issued-At timestamp.
  • nonce: Mitigates replay attacks by binding client request to token.
  • Scopes: openid (mandatory), profile, email, address.
  • Claims Mapping: Mapping IdP claims to internal app roles/attributes.
OIDC Authorization Code Flow (Authentication + Token Issuance) Sequence Flow
1
RP → OP
Relying Party redirects user to OP authorization endpoint with scope=openid profile email, response_type=code, and nonce.
2
End-User & OP
User authenticates at OP (login + MFA) and consents to share profile/email with the Relying Party.
3
OP → RP
OP sends an HTTP 302 redirect back to RP's redirect URI with a short-lived Authorization Code.
4
RP → OP (Token Endpoint)
Back-Channel POST: RP presents Auth Code, client_id, and client_secret to the OP token endpoint.
5
OP → RP Response
OP validates credentials and returns both an ID Token (JWT) and an Access Token.
6
RP Validation & UserInfo
RP verifies ID Token signature (iss, aud, exp, nonce). Optionally calls /userinfo with Access Token for additional claims.
Synthesis 04

Architectural Comparison: SAML 2.0 vs. OAuth 2.0 vs. OIDC

Side-by-side Matrix
Dimension SAML 2.0 OAuth 2.0 OpenID Connect (OIDC)
Primary Purpose Cross-domain Enterprise Single Sign-On (SSO) and federation. Delegated authorization for APIs without credential sharing. Federated user authentication and identity assertion for modern apps.
Main Mechanism / Token XML Assertion (digitally signed XML document with assertions). Access Token (opaque string or JWT) + Refresh Token. ID Token (always a signed JSON Web Token - JWT) + Access Token.
Authentication (AuthN) Native & Central: Contains AuthnStatement detailing how/when user logged in. No: Explicitly NOT an authentication protocol (only handles permissions). Yes: Purpose-built identity extension layered directly over OAuth 2.0.
Authorization (AuthZ) Limited (coarse-grained attribute release to SP). Core Speciality: Fine-grained delegated authorization via scopes. Inherits OAuth 2.0 scope-based delegated API authorization.
Data Format & Transport XML, XML-DSig, heavy payloads via HTTP POST/Redirect bindings in browser. JSON, HTTP Authorization Bearer headers, back-channel API calls. JSON, REST, JWT, lightweight headers; optimized for web & mobile.
Typical Use Case Legacy & enterprise B2B SaaS (Salesforce, Workday, internal corporate portals). Securing REST APIs, third-party app integrations (e.g., “Allow app to read calendar”). Modern web/mobile apps, consumer SSO (“Sign in with Google/Apple”), SPA auth.
Day 1 Review 05

Key Takeaways for Verbal Revision

6 Essential Lessons
Takeaway 1 • Enterprise SSO
SAML 2.0 is the enterprise powerhouse: Built on XML and digital signatures, it excels at browser-based web SSO between an IdP and enterprise Service Providers (SPs).
Takeaway 2 • AuthN vs AuthZ
OAuth 2.0 is authorization, NOT authentication: It solves delegated API access using scoped tokens. Using OAuth alone to prove user identity is an insecure anti-pattern.
Takeaway 3 • The OIDC Bridge
OIDC standardizes identity on OAuth: By adding the openid scope and an ID Token (JWT), OIDC gives clients verifiable proof of user authentication.
Takeaway 4 • Token Destination Rule
Know who consumes which token: ID Tokens are consumed by the Client/RP for user profile info; Access Tokens are consumed by the API/Resource Server for authorization.
Takeaway 5 • Secret Protection
Auth Code flow keeps secrets safe: By splitting the flow into a front-channel code and back-channel token exchange, credentials and tokens avoid exposed browser address bars.
Takeaway 6 • Format Evolution
XML to JSON/JWT transition: While SAML’s XML works reliably for enterprise desktop browsers, OIDC’s lightweight JSON/JWT design makes it ideal for mobile, SPAs, and microservices.
