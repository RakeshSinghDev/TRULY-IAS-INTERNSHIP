SAML 2.0 Federation

Security Assertion Markup Language — an XML-based standard for exchanging authentication and identity information between organizations and security domains.

Core Goal

Primary Objective

Allows an Identity Provider (IdP) to authenticate a user and provide a SAML Assertion to a Service Provider (SP), enabling Single Sign-On (SSO) across applications.

Trust Architecture

Circle of Trust & ACS

A group of IdP(s) and SP(s) with an established trust relationship. The ACS (Assertion Consumer Service) is the SP endpoint that receives and parses the SAML Response/Assertion.

Main Entities

The three primary actors in SAML federation.

User / Principal
Human end-user who requests access to an application.
Identity Provider
Authenticates user, maintains identity, and issues SAML assertions.
Service Provider
Requests auth, validates assertion, and grants protected access.

SAML Assertion & Components

XML document issued by the IdP containing authentication result and user attributes.

  1. Subject: Identifies the user (usually in the form of a NameID).
  2. Conditions: Defines the validity period, audience, and other restrictions.
  3. AuthnStatement: Contains information about how and when the user was authenticated.
  4. AttributeStatement (optional): Contains user attributes (e.g., name, email, role, department, etc.).
  5. Signature: Digitally signed by the IdP to ensure integrity and authenticity.

SP-Initiated SSO Flow (HTTP POST)

  1. AuthnRequest: User attempts access; Service Provider sends an AuthnRequest to the IdP.
  2. Authenticate User: Identity Provider challenges the user and verifies credentials.
  3. SAML Response (Assertion): IdP issues a digitally signed SAML Response containing the assertion back to the SP.
  4. Create Local Session: SP validates the assertion and creates a local session, granting access to the application.

Key Advantages of SAML 2.0

  • Enables secure Single Sign-On (SSO) across multiple applications.
  • Based on open standard (OASIS).
  • Widely supported by enterprise providers (Okta, Azure AD, ADFS, etc.).
  • Supports attribute-based access control.
  • Uses digital signatures to prevent tampering.
02

OAuth 2.0

An authorization framework that allows a client application to access protected resources on behalf of a resource owner without sharing credentials.

Framework Purpose

Primary Objective

Provides a secure, standard way for a client application to obtain limited access to user resources using an access token issued by an authorization server.

Token Mechanics

Stateless Token Format

Usually a JWT (JSON Web Token) carrying claims: sub, aud, scope, exp, iat. Advantage: validated without the AS storing info about every token.

Main Players

Resource Owner
User — the person who owns the data / resource.
Client
Application requesting access on behalf of user.
Authorization Server
Authenticates user, obtains consent, issues tokens (e.g. in ForgeRock AM).
Resource Server
Hosts protected resources (APIs) and validates tokens.

Token Types

API Access

Access Token

Credential issued by AS that allows the client to access protected resources. Usually short-lived, sent to RS using Bearer token, and represents granted scopes/permissions.

Renewal

Refresh Token

Used by the client to obtain a new access token when the current access token expires without requiring user re-authentication.

High-Level OAuth 2.0 Flow

  1. Authorization Request: Client directs user to Authorization Server (e.g., login, consent).
  2. Authentication + Consent: User authenticates and grants requested permissions.
  3. Authorization Code: Authorization Server returns a short-lived authorization code to the Client.
  4. Exchange Code for Access Token: Client exchanges authorization code at the AS token endpoint.
  5. Access Token (+ Refresh Token): Authorization Server returns Access Token and optional Refresh Token.
  6. Access Token Sent to Resource Server: Client presents Access Token as a Bearer token.
  7. Protected Resource Returned: Resource Server validates token and serves protected resource.

OpenID Connect (OIDC)

Identity layer built on top of OAuth 2.0 to authenticate users and obtain profile information.

OIDC = OAuth 2.0 + Authentication + Identity
OAuth 2.0 → Authorization (provides access to protected resources)
Authentication → Proves who the user is
Identity → Provides basic profile information
Core Concept

Main Idea

OAuth 2.0 provides access to protected resources. OIDC builds on OAuth 2.0 and adds standardized authentication and identity information.

Identity Verification

Primary Objective

Allow a client to verify the identity of an end user and obtain basic profile attributes.

What OIDC Provides

Four core capabilities layered onto the OAuth 2.0 framework.

Authentication
Verifies and asserts the identity of the end user.
ID Token (JWT)
Digitally signed token carrying verified user identity claims.
UserInfo Endpoint
Protected endpoint used to obtain additional profile data.
Built on OAuth 2.0
Reuses OAuth 2.0 endpoints, tokens, and authorization code flows.

OIDC Players

The three interacting roles in an OpenID Connect exchange.

End User
Human user being authenticated.
Relying Party (RP)
Client application relying on the OIDC Provider.
OIDC Provider
Authorization Server that authenticates user and issues tokens.

Key Endpoints

Standardized HTTP endpoints defined in the OpenID Connect specification.

Part B • Actual Sequence

  1. Client sends authorization request: Client initiates flow with client_id, scope=openid, and redirect_uri to the OIDC Provider.
  2. User authenticates and gives consent: End user verifies credentials and approves requested scopes.
  3. Authorization Code is returned: OIDC Provider redirects back to client callback with temporary authorization code.
  4. Client exchanges code for tokens: Client presents authorization code at /token to receive ID Token + Access Token (and optional Refresh Token).
  5. Client requests UserInfo using Access Token: Client makes an authorized request to the /userinfo endpoint.
  6. User profile information is returned: OIDC Provider validates token and delivers verified user profile claims.

Key Takeaways

Core principles to review before the 5-minute explanation walkthrough.

01
SAML 2.0 is an XML-based federation standard allowing an IdP to authenticate users and issue assertions to an SP for enterprise Single Sign-On.
02
SAML Assertion comprises 5 distinct components: Subject (NameID), Conditions, AuthnStatement, AttributeStatement, and IdP Signature.
03
OAuth 2.0 is strictly an authorization framework enabling client applications to obtain limited access to protected APIs using access tokens without sharing credentials.
04
Stateless Access Tokens (usually JWT) carry claims (sub, aud, scope, exp, iat) validated by the Resource Server without database lookups.
05
OIDC Formula: OIDC = OAuth 2.0 + Authentication + Identity. It standardizes user authentication on top of OAuth 2.0.
06
ID Token vs. Access Token: The ID Token (JWT) is used by the client for user identity/authentication, whereas the Access Token is sent to Resource Servers for API authorization.
07
OIDC Endpoints: Standardizes /authorize, /token, /userinfo, /jwks, and optional /end_session for full identity lifecycle management.
